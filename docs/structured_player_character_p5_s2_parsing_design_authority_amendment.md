## 2. Established contradiction

The following are established facts, not future authorization:

1. The frozen JSON request represents `contract_version` as the JSON string
   `"structured-player-character/v1"`.
2. `CharacterCreationCommand` is intentionally strict. Its model graph uses
   the existing strict configuration and `PlayerCharacterContractVersion` is a
   string-valued enum.
3. `CharacterCreationCommand.model_validate_json(...)` accepts the frozen JSON
   representation. Pydantic JSON-mode validation converts the valid JSON enum
   string to the required `PlayerCharacterContractVersion` instance.
4. Ordinary FastAPI body binding first reads and JSON-decodes the body and then
   submits the resulting Python values to the body model.
5. That ordinary body-field path validates the nested strict model in Python
   mode. The decoded Python string is not already a
   `PlayerCharacterContractVersion` instance, so validation rejects the valid
   frozen wire value.
6. The rejection occurs during dependency/body solving, before
   `create_player_character` executes.
7. Consequently, the otherwise-valid frozen request cannot reach raw
   `Idempotency-Key` validation, `PlayerCharacterOperationId` construction,
   `PlayerCharacterService.create`, first-success translation, exact replay,
   conflict handling, or persistence.
8. `Body(strict=False)` and equivalent ordinary parameter-annotation variants
   alter only the outer FastAPI field metadata. They do not override the
   nested strict configuration of `CharacterCreationCommand`, and the same
   Python-mode rejection remains.

This is:

- not a defect in `docs/public_client_contract.md`;
- not a defect in `CharacterCreationCommand`;
- not a reason to weaken strict validation;
- not a persistence, service, receipt, fingerprint, replay, allocation,
  ownership, controller-authority, Unit-of-Work, or transaction defect; and
- specifically an approved P5-S2 transport parsing and executable
  direct-binding design defect.

The installed versions against which this behavior was reproduced are:

| Package | Version |
| --- | --- |
| FastAPI | `0.139.2` |
| Starlette | `1.3.1` |
| Pydantic | `2.13.4` |
| pydantic-core | `2.46.4` |

Read-only source inspection confirms the relevant sequence:

- Starlette `Request.body()` consumes the ASGI request stream and caches the
  concatenated bytes;
- FastAPI's routing layer conditionally JSON-decodes a declared body before
  dependency solving;
- FastAPI's body-field solver validates that already-decoded Python value;
- Pydantic's `model_validate_json` instead delegates the raw bytes to the
  JSON-mode validator; and
- FastAPI deep-merges route `openapi_extra` into the generated operation.

No framework or installed-package modification is needed or authorized.

## 4. Exact future route-boundary design

After separate approval and implementation authorization, the endpoint
signature shall be exactly:

```python
async def create_player_character(
    http_request: Request,
    idempotency_key: PlayerCharacterIdempotencyKeyHeader,
    principal: RequestPrincipal = Depends(get_current_principal),
    service: PlayerCharacterService = Depends(get_player_character_service),
) -> PlayerCharacterSelfProjection:
```

`CharacterCreationCommand` shall not appear as a route parameter. There shall
be no `Body(...)` parameter and no other executable FastAPI request-body
field.

The exact future raw-body-route flow shall be:

1. The raw ASGI request reaches the existing normal-application route. The
   existing normal-application route-registration condition remains the only
   activation seam. No second router or composition root is introduced.
2. `get_current_principal` resolves the trusted `RequestPrincipal`.
3. `get_player_character_service` resolves the existing
   `PlayerCharacterService`.
4. FastAPI performs declarative `Header` extraction and validation of
   `idempotency_key` as `PlayerCharacterIdempotencyKeyHeader`.
5. Only after both dependencies and the declarative header succeed does the
   route enter. FastAPI supplies the trusted Starlette/FastAPI `Request` but
   performs no decoding or direct binding of `CharacterCreationCommand`.
6. On route entry,
   `_validate_player_character_creation_transport(http_request,
   idempotency_key)` runs exactly once.
7. That existing helper validates raw `Content-Type` occurrence, bytes, and
   media type first.
8. The same helper then validates raw `Idempotency-Key` occurrence, exact
   bytes, ASCII, length, alphabet, and equality to the declaratively bound
   value.
9. Only after both raw-header checks, the helper constructs and returns exactly
   one `PlayerCharacterOperationId`. This construction intentionally precedes
   body receipt and command validation.
10. Only after transport acceptance, the route executes
   `raw_body = await http_request.body()` exactly once. No other production
   code reads, streams, decodes, reparses, or replaces the body.
11. The route passes those exact cached bytes once to
   `_parse_player_character_creation_command(raw_body)`.
12. That helper invokes exactly
   `CharacterCreationCommand.model_validate_json(raw_body)`.
13. Successful JSON-mode parsing returns the exact existing strict
   `CharacterCreationCommand`. No adapter DTO, duplicate public model,
   dictionary-to-model second pass, domain-model change, or validation-graph
   duplication is introduced.
14. Only successful parsing permits the route to invoke
    `PlayerCharacterService.create(...)` exactly once with
   the dependency-provided principal, the one operation ID, and the exact
   parsed command.
15. Existing `CreationSuccessResult` projection, exact replay behavior,
    protocol-decision translation, exception propagation, sanitization, and
    cancellation propagation remain unchanged.

The body is therefore consumed once at the trusted request boundary and
validated once in the mode that corresponds to its wire representation.
Starlette's internal body cache is not an authorization for a second
application read.

The selected order is normative:

`raw ASGI request → get_current_principal → get_player_character_service →
declarative FastAPI Header extraction/validation of idempotency_key → route
entry → raw Content-Type validation → raw Idempotency-Key
occurrence/byte/bound-equality validation → exactly one
PlayerCharacterOperationId construction → exactly one Request.body()
application call → CharacterCreationCommand.model_validate_json validation →
exactly one PlayerCharacterService.create invocation`

Both dependencies precede declarative header validation and every body
validation step. A dependency failure may therefore pre-empt a malformed body.
Declarative header failure may pre-empt route entry and body receipt. After
route entry, `Content-Type` validation precedes raw-key validation; raw-key
validation precedes operation-ID construction and body receipt; operation-ID
construction intentionally precedes body receipt and command validation; and
parsing failure precedes and prevents service invocation. The frozen public
contract is silent on precedence when more than one input is invalid. This
amendment narrowly authorizes the reproduced precedence above without changing
dependencies, authentication, service behavior, or public errors.

All invalid paths stop before the service call. The construction of a local
operation-ID value before later body rejection has no persistence,
authorization, receipt, or transaction effect.

values, internal model names, exception strings, stack traces, field details,
or distinction useful for enumeration.

The exact classifications are:

| Condition | Exact boundary | Translation |
| --- | --- | --- |
| Missing, duplicate, ambiguous, or non-JSON `Content-Type` | Existing raw transport helper before body consumption | Existing `_request_validation_failure` and handler; fixed 422 |
| Missing, empty, overlength, alphabet-invalid, comma-combined, or a single non-ASCII `Idempotency-Key` | Declarative FastAPI `Header` validation after both dependencies and before route entry | Existing request-validation handler; fixed 422; raw helper is not reached |

| A raw `Idempotency-Key` that passes declarative validation but fails raw occurrence, exact-byte, ASCII, length, alphabet, or bound-value equality checks | Existing raw transport helper after both dependencies, declarative header validation, and route entry, but before operation-ID construction and body receipt | Existing `_request_validation_failure` and handler; fixed 422 |
| Absent body | `Request.body()` yields the same zero-length bytes as an empty submitted body | JSON-mode `ValidationError`; fixed 422 |
| Explicit empty body | The exact bytes are `b""` | JSON-mode `ValidationError`; fixed 422 |
| Malformed or truncated JSON | Pydantic JSON parser | JSON-mode `ValidationError`; fixed 422 |
| Invalid top-level JSON array, scalar, string, number, boolean, or object shape | Strict command JSON-mode validation | `ValidationError`; fixed 422 |
| Top-level JSON `null` | Strict command JSON-mode validation | `ValidationError`; fixed 422 |

| Unknown top-level or nested fields | Existing `extra="forbid"` graph | `ValidationError`; fixed 422 |

| Invalid enum string | Existing exact enum validation in JSON mode | `ValidationError`; fixed 422 |
| Explicit null where a declaration or required field is required | Existing strict command graph | `ValidationError`; fixed 422 |

Absent and explicitly empty bodies are deliberately not publicly
distinguished. At the selected trusted seam both are zero-length raw content,
both violate the required JSON command contract, and both receive the same
sanitized response.

No raw transport-size limit is added or authorized. `Request.body()` buffers
the full raw request before validation, and the 65,536-byte limit applies to the
canonical declaration envelope, not raw wire bytes. Full-request buffering and
the difference between canonical size and raw-wire size remain explicit
residual risks. This amendment does not broaden or redefine `Content-Encoding`
handling or duplicate-JSON-member behavior.

The parsing helper catches only Pydantic `ValidationError`. It does not catch
`BaseException`, `CancelledError`, or arbitrary body-read failures. A
disconnect, ASGI receive failure, framework defect, or other unexpected
request-read exception is not safely reclassified as submitted model
invalidity and therefore follows existing exception and cancellation
boundaries. Cancellation is never translated. No exception string is exposed.

The application layer does not duplicate enum, declaration, Unicode,
conditional-value, canonical-size, or other domain validation.
`CharacterCreationCommand` remains strict.

Raw helpers execute only after both dependencies and declarative `Header`
validation succeed. This amendment does not move all header validation into the
route. Header-classification tests must not claim that missing, empty,
overlength, alphabet-invalid, comma-combined, or a single non-ASCII value
reached `_raw_header_values` or
`_validate_player_character_creation_transport` when declarative validation
already rejected it.
